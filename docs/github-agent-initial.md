# Исходная реализация согласованной спецификации

Режим #42 выключен до настройки App и контролируемой живой проверки человеком.
Переменная `IMPLEMENTATION_INITIAL_ENABLED=true` включает маршрут; до этого
новая команда не вызывает модель реализации. Обсуждение, триаж, публикация
спецификаций и тикетов и `/oc fix` сохраняют прежние маршруты.

В исходном issue человек оставляет отдельный комментарий:

```text
/oc implement-spec spec=#123 tickets=#124,#125 approve
```

Это одновременно явное согласование спецификации, полного списка тикетов и
команда реализации. Ссылка на текущий комментарий берётся из события.
Для ранее оставленного согласования того же формата можно указать:

```text
/oc implement-spec spec=#123 tickets=#124,#125 approval=https://github.com/MeNn13/ai-for-developers-project-387/issues/100#issuecomment-123456
```

Согласование должно принадлежать доверенному человеку в исходном issue.
Разрешение опубликовать тикеты и создание спецификации не заменяют его.
Тикеты должны совпадать с нативными sub-issues спецификации; зависимости
читаются через blocked-by. Внешние блокеры должны быть закрыты. Цикл,
неполная история, неоднозначность и недоступное основание останавливают работу
до модели. Текущий формат команды намеренно строгий.

## Исполнение и публикация

Фиксированный шаг `opencode.yml` отправляет dispatch в
[opencode-implement.yml](../.github/workflows/opencode-implement.yml), передавая
номера issue и комментария и digest исходного текста. Workflow читает комментарий заново,
проверяет автора и загружает контекст. Код и конфигурация стадий закреплены на
одном SHA main. Снимки описаний, обсуждений, согласования, графа и идентификаторов
сохраняются в `implementation-context` на семь дней.

Linux-контроллер выполняет доступный фронтир последовательно: отдельная новая
read-only сессия закреплённого CLI на тикет, ограниченные данные файлов, настоящий
Git-коммит и полный `mise run check` через существующий Bubblewrap. Независимые
тикеты также исполняются последовательно. Shell, запись, MCP и делегирование
инструментами модели отключены. Контроллер передаёт результаты между сессиями.
Локальная процедура [Windows](agents/windows.md) сохраняется.

После первого проверенного результата отдельный издатель создаёт draft PR через
[контракт App](github-agent-publisher.md), сверяя основания, граф и ожидаемый head.
Остальной граф продолжается с опубликованного родителя. Базы, SHA, команды,
результаты и чистота интеграций записываются в `initial-first-evidence` и
`initial-final-evidence`. Один фазовый коммит публикуется после каждой стадии;
промежуточные SHA остаются свидетельствами локальных интеграций. Опубликованная
история не переписывается.

Отдельные новые сессии выполняют Standards и Spec review всего графа.
Подтверждённые дефекты исправляются проверенными коммитами. Финальный коммит
снова проходит полный check точного SHA. Только успешный
`implementation-final-check` позволяет перевести PR в ready. PR содержит
источники, согласование, закрывающие ссылки, SHA, команды, Actions, риск последствий
и откат; для данных объясняется достаточность отмены кода. Внутреннее ревью не
заменяет независимое авторевью и браузерную приёмку GitHub.

Модель не получает токен GitHub или ключ App. Обе публикации используют
environment `implementation-publisher` с человеческим approval. Контекст задаёт
единый deadline 60 минут; ожидания approval входят в него. Контроллер ограничивает
модель и проверки оставшимся временем, издатель отвергает просроченный результат.
Linux timeout останавливает группу процессов. Отдельный обработчик завершения
получает своё время после остановки.

## Отказы и восстановление

Concurrency сериализует обращение. История отклоняет запрос, поступивший во время
предыдущего исполнения, даже при обработке после его окончания. Исходный запуск
не использует маркеры бюджета PR и не расходует три попытки исправлений #41.

`implementation-completion` независимо опрашивает завершённые запуски и сообщает
в исходном issue причину, последний известный SHA и ссылку на attempt, без модели
и исполнения артефактов. При раннем сбое известен только base. Неопределённая
причина не уточняется. Расписание Actions может задерживаться; обработчик можно
запустить вручную из main.

После остановки человек изучает логи и оставляет новую команду. Автоматического
повтора нет; полный и частичный Re-run исходного исполнения отклоняются.
Если draft уже создан, используйте `/oc fix <publisher-run-id>` с
receipt либо согласуйте ручное продолжение. Найденная ветка автоматически не
присваивается. Чужой head, истёкший receipt и изменение требований требуют решения
человека. Материальное изменение основания требует нового согласования.
Force/reset, автомерж и обход фильтра запрещены. Защищённая инфраструктура
меняется отдельным человеческим PR.

## Граница доказательств

Локальные API/CLI fixtures проверяют согласование, отказы, реальные Git-коммиты
графа и передачу draft/ready. Модель и Linux-проверка заменены внешними адаптерами.
Это не живые субагенты и не проверка провайдера, Bubblewrap, App, approval или CI.

Человек проверяет App и права по руководству издателя, готовит отдельную
согласованную учебную фичу и выполняет настоящий цикл: команда, первый draft,
граф, ready, CI, независимое авторевью и браузерный артефакт точного head.
Ссылки на исходное issue, согласование, runs и PR сохраняются как свидетельства.
До этого живая оркестрация остаётся непроверенной и режим остаётся выключенным.
Новая инфраструктура не применяется для изменения собственных ограничений.
