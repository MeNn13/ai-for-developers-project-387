# Исправления PR по команде человека

Режим #41 по умолчанию выключен. После настройки App и контролируемой проверки
настоящего PR человек задаёт repository variable `IMPLEMENTATION_REPAIR_ENABLED=true`.
Наличие workflow и локальные фикстуры не подтверждают живую приёмку.

В общем либо построчном комментарии App PR написать
`/oc fix <publisher-run-id> <описание исправления>`.
Номер — последний запуск с артефактом `implementation-publication`, который
подтверждает текущий head и PR. Для старого receipt без `sourceRunId` требуется
ручное продолжение; найденная ветка или текст PR не заменяют receipt.
Обычные вопросы `/oc` продолжают использовать режим обсуждения.

Допускается только доверенный человек из существующего allowlist, PR настроенного
App в `spec/<spec>` того же репозитория с base `main`. Контекст включает исходное
обращение, спецификацию, тикеты, неизменное согласование, обсуждение PR и diff.
Построчное обращение сохраняет путь, номер, сторону, commit и фрагмент diff.
Изменившееся основание останавливает продолжение до нового согласования.

## Допуск и бюджет

Каждое задание заново проверяет допуск перед установкой CLI, моделью, проверкой
или выдачей App token. Источник счётчика — полная история Actions и успешный
шаг `implementation-admitted` в доверенных заданиях с номером PR в имени.
Артефакты и комментарии не определяют бюджет. Несколько заданий одного
`run_attempt` расходуют одну попытку. Полный или частичный Re-run, включая только
издателя, получает новый допуск и расходует следующую попытку.

На PR разрешены три попытки. Отмена, timeout, отсутствие ключа и ошибка установки
после маркера расходуют попытку. Четвёртый допуск возвращает `limit_exhausted`.
Недоверенный запрос, обычный вопрос и busy-отказ попытку не расходуют.
Построчный запуск GitHub может хранить SHA merge ref или SHA ветки PR.
Для merge ref основанием служит первый родитель merge-коммита. Для SHA ветки
проверяется привязка запуска к PR того же репозитория и происхождение SHA от
зафиксированной базы PR. В обоих случаях основание должно входить в историю main,
а файл workflow должен совпадать с версией на основании. Обновление main
не обнуляет бюджет и не делает прежние построчные допуски недоверенными.
Неизвестное происхождение или изменённый workflow останавливают цепочку.
Проверяется время поступления комментария: запрос во время активного запуска
получает «дождитесь завершения», даже если обработан позже. Задания сериализованы
на PR и не отменяют активную работу. Неполная история, ошибка API или неполный
список jobs останавливают выполнение. Удаление всей истории администратором
обнаружить невозможно; гарантия зависит от её сохранности и доверенной конфигурации.
Новый PR получает свой бюджет; независимое ревью его не расходует.

Артефакты имеют точные имена в пределах run и загружаются с `overwrite: true`:
полный Re-run заменяет данные выполненных стадий, частичный использует сохранённые
данные успешных стадий. Параллельные попытки одного комментария сериализованы.
Загрузки не используют шаблоны имён и привязаны к конкретному run; издатель
повторно сверяет контекст, digest, SHA и свежий допуск текущей попытки.
Повтор одного издателя заменяет receipt; отсутствие файла после сбоя запрещает
продолжение и требует ручного разбора, а не поиска произвольного старого receipt.
При повторе издателя после записи ветки читается checkpoint текущего run:
API должен вернуть ровно один неистёкший артефакт с точным именем и run ID,
затем скачивается его конкретный artifact ID. Receipt текущего run восстанавливает
незавершённую операцию PR без второго коммита и обновления ref. Чужой receipt,
неполный список артефактов или изменившийся head останавливают восстановление.
Обычные построчные обсуждения и допуски других PR не входят в бюджет этого PR;
происхождение истории проверяется для соответствующих маркеров допуска.

### Разбор сбоя и повтор

1. Откройте конкретную попытку Actions и шаг **Fresh admission for this job and run attempt**
   в задании, где произошёл сбой. При повторе только издателя это
   `implementation-publish-pr-<номер>`. Нажмите на заголовок шага и скопируйте его URL,
   затем проверьте `implementation-admitted` во всех заданиях попытки. В логе и Step Summary
   `untrusted_origin` означает отказ проверки происхождения, `invalid_history` —
   недоступную или некорректную историю, `gate_error` — другой сбой до допуска.
   Запишите `attempt` и `sha` из диагностики. Названия шагов есть в
   [workflow ремонта](../.github/workflows/opencode.yml).
2. На странице запуска издателя откройте артефакт `implementation-publication`.
   Сверьте `publication.json` с номером PR и текущим head. Для нового комментария
   возьмите `publisherRunId` из этого receipt. Скопируйте ссылку на артефакт из
   списка **Artifacts**. Если подходящего receipt нет,
   требуется ручной разбор. См. [проверку receipt и публикацию](github-agent-publisher.md).
3. В запуске [браузерной приёмки](../.github/workflows/browser-acceptance.yml)
   откройте артефакт `browser-pr-<номер>-<head>-<run>-<attempt>`, загруженный шагом
   **Upload browser evidence and traces**. Сверьте `expectedSha` и `actualSha` из
   `evidence.json` с head из receipt и сохраните ссылку на артефакт вместе с
   `runUrl`. SHA запуска из диагностики допуска может относиться к другой ревизии.
4. Если в попытке уже есть успешный `implementation-admitted`, она израсходована.
   Повтор только издателя получает новый `run_attempt` и расходует ещё одну
   попытку при успешном допуске. Если сбой произошёл до маркера во всех заданиях
   попытки, бюджет сохраняется. После устранения причины отправьте новый
   построчный `/oc fix <publisher-run-id> <описание>` с receipt текущего head.

## Изоляция и публикация

Модель читает доверенный checkout и выдаёт ограниченный JSON с файлами. Она
использует закреплённую бесплатную модель и не получает GitHub token или App key.
Shell, запись файлов, MCP и субагенты отключены существующей конфигурацией.
Модель не может формировать context или verification. Автоматических повторов нет.

Отдельное задание фильтрует пути до записи, собирает новый коммит поверх точного
head и выполняет `mise run check`. Проверка запускается через Bubblewrap:
checkout, служебные файлы runner и свидетельства доступны только для чтения,
запись разрешена в build outputs, `artifacts` и временный каталог.
У процесса нет ключа модели и токена записи. Неуспех изоляции запрещает публикацию.
Для исходной ветки с изменившимися защищёнными файлами нужен человек.
Управляющий checkout остаётся на фиксированном SHA main. Точный head PR размещается
в отдельном worktree; до установки зависимостей проверяется его diff от общего
предка с main, включая режимы файлов. Обновлённые только в main управляющие файлы
не считаются изменениями автора. Конфигурация проверок и генератор кандидата
сохраняют проверенный защищённый baseline, а допуск, сборка коммита, изоляция
и запись свидетельства исполняются скриптами фиксированного управляющего checkout.

Издатель использует только доверенную основную ревизию, повторяет допуск и проверяет
маркер текущей попытки в Actions. Публикует новый Conventional Commit в прежнюю
ветку без force. Проверка связана с полным результатом и точным SHA; чужое
обновление head останавливает публикацию. Исправление остаётся draft до отдельного
общего ревью графа. Даже ранее готовый PR возвращается в draft при `ready:false`.
Receipt дополнен `sourceRunId` для получения исходных доверенных оснований.
Ручной workflow издателя не принимает ремонтный результат в обход цепочки.

## Независимое завершение

`implementation-completion` каждые пять минут читает доверенную историю завершённых
запусков, а также доступен через Run workflow из main. Он публикует последний
известный SHA, ссылку на attempt и причину: `limit_exhausted`, `busy`, `cancelled`,
`timeout`, `infra`, `agent_failed`, `success` либо `unknown`.
Он не исполняет код PR и не читает артефакты. Задержка отчёта зависит от планировщика
Actions; расписания GitHub могут задерживаться. Повторный проход не дублирует
собственный комментарий. Причина определяется только проверяемыми стадиями,
не произвольным текстом ошибки. После исчерпания бюджета продолжает человек.

Расписание выбрано потому, что `workflow_run` запрещён текущим линтером без
отдельного человеческого исключения. Новых исключений для режима нет.
Контролируемая проверка App PR, Bubblewrap на hosted Linux, отмена, timeout и
частичные Re-run остаются необходимой живой приёмкой до включения режима.
