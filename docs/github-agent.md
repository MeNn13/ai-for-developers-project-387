# Агент в GitHub Actions

[Обзор проекта](../README.md).

## Ручной вызов и доступ

Workflow [opencode.yml](../.github/workflows/opencode.yml) отвечает на команды
`/oc` и `/opencode` в начале нового комментария к issue, PR или строке diff.
Регистр команды не важен; редактирование комментария не запускает агента.
Пример: `/oc explain this issue`.

Вызов разрешён только `MeNn13`; список `allowedUsers` находится в
`scripts/opencode-publish.mjs` (общий для допуска и издателя). Для расширения
добавить GitHub-логин в список и слить
изменение. Участник также должен иметь роль OWNER, MEMBER или COLLABORATOR.
Комментарии ботов и обращения к PR из fork игнорируются. Недопущенные вызовы
не получают ключ модели.

Используется OpenCode CLI **2.2.3** с проверкой SHA-256 релизного архива,
модель — **`opencode/glm-5.3-flash-free`**. Ключ хранится только в секрете
репозитория **`OPENCODE_API_KEY`**. Карта, пополнение и платные модели не нужны.
Бесплатный доступ ограничен условиями провайдера и может закончиться; при
лимите или недоступности модели прогон завершается ошибкой, платного резерва нет.
Основная модель и вспомогательные агенты явно используют ту же бесплатную модель.

Это собственный workflow с CLI: прежний OpenCode GitHub Action
[больше не поддерживается](https://github.com/anomalyco/opencode/pull/59032).
Установленное OpenCode GitHub App для этого варианта не используется.
Авторизация GitHub — встроенный `GITHUB_TOKEN`, поэтому `id-token: write`
не нужен. Checkout имеет `persist-credentials: false`. Задания получения контекста
и модели имеют только права чтения; отдельное задание публикации имеет
`issues: write` и `pull-requests: write`. Оно запускает проверенный скрипт издателя
из той же ревизии основной ветки, не запускает модель и не исполняет её вывод.

Агент читает код основной ветки,
`AGENTS.md`, `docs/agents/`, глоссарий, ADR и проектные скиллы из `.agents/skills`.
По явному запросу применяет скиллы `triage`, `to-spec` и `to-tickets`; отдельного
парсера команд скиллов нет. Модель готовит текст и структурированный результат,
а отдельный `publish` создаёт спецификацию или согласованные тикеты в этом
репозитории. Изменения кода и PR отключены. Shell, редактирование, субагенты
и MCP запрещены. Для PR передаётся diff как текст, код его ветки не исполняется.
GitHub-токен не передаётся процессу модели. Настройки локального Codex остаются
отдельными от конфигурации CI в `.github/opencode/opencode.json`.

Ответ появляется обычным комментарием от `github-actions[bot]` со ссылкой на
прогон; комментарии к diff также получают ответ в общем обсуждении PR.
Вкладка **Actions → opencode** показывает состояние. Передаются описание,
обсуждение до вызывающего комментария и, для PR, diff и соответствующая ветка
review-обсуждения. Ревизия основной ветки записывается в контекст вызова.
Для issue также загружаются связанные issues текущего репозитория с обсуждениями:
ссылки вида `#123` и полные URL, на два уровня, не более 30 связанных issues.
Удалённые и недоступные связанные issues отмечаются в контексте явно;
обычное обсуждение продолжается, публикация тикетов по ним запрещена.
Слишком большой контекст отклоняется явно. Следующий вызов заново читает
обсуждение; скрытая память предыдущей сессии не используется.

## Диагностика и восстановление

При сбое подготовки в логах остаётся только безопасная диагностика,
а отдельный `opencode-diagnostic` с `diagnostic.json` хранится один день и
передаётся издателю даже при failure (кроме cancellation). Категории: запуск и
выход CLI, размер и JSONL потока, незавершённый ответ, JSON и схема ответа,
ошибка провайдера, чтение/запись файлов, конфигурация и неизвестная ошибка.
Авторизация и HTTP 429 различаются только по структурированному статусу
провайдера; текст ошибки не служит доказательством исчерпания лимитов.
Сырые ответы, stderr, контекст и ключи в диагностику не попадают.
Для `reply_json` версия 2 содержит `details`: размеры `streamBytes` и
`answerBytes` в UTF-8, `candidateChars` и `position` в единицах UTF-16
(позиция может быть `null`), счётчики `eventCount`, `textEventCount`,
`messageCount`, `finalTextEventCount`, фиксированные категории `wrapper`,
`root` и `parseKind`. Идентификаторы сообщений и текст ошибки не сохраняются.
Для `reply_schema` версия 2 содержит только `details.rule` — фиксированный
код первого нарушенного правила: `version_comment`, `publication_kind`,
`publication_items`, `spec_item_count`, `ticket_references`, `item_key`,
`item_text`, `item_blockers`, `blocker_order`, `spec_blockers`.
Непредвиденное исключение валидатора обозначается `schema_other`.
Значения полей ответа и текст исключения не сохраняются. Эта диагностика
не восстанавливает причину прежнего сбоя без исходного ответа модели.
Остальные ошибки используют версию 1; издатель понимает обе версии,
включая прежнюю диагностику `reply_schema` версии 1.
Новая диагностика схемы версии 3 содержит только фиксированные `rule`, `field`
и `reason`: `missing`, `type`, `empty`, `too_long`, `invalid`, `duplicate_key`,
`duplicate_dependency`, `reference`. Комментарий на русском объясняет причину
и называет поле, не раскрывая его значение. Старые версии 1/2 читаются по-прежнему.
Для диагностики откройте Actions по ссылке комментария, затем прочитайте только
`opencode-diagnostic/diagnostic.json`; сырой вывод модели для этого не нужен.
Синтетические тесты проверяют программу на вымышленных ответах и не доказывают,
что будущая модель соблюдёт протокол.
Размер диагностики ограничен 1024 байтами. Счётчики не доказывают причину
сбоя сборки потока и не восстанавливают причины исторических ошибок.
При известном сбое подготовки публикация не начиналась: передайте ссылку
на Actions для диагностики, вместо повторения запроса без новых данных.
При отсутствии или некорректной диагностике выводится общее сообщение.
Диагностика публикации версии 3 содержит фиксированные `reason` и `state`:
`none` означает, что восстановление проверено и записи ещё не отправлялись,
`possible` — найдены прежние объекты или уже отправлена запись,
`unknown` — прежнюю публикацию исключить нельзя. Ошибка первой записи считается
возможной публикацией даже при потере ответа GitHub. Если подготовка при повторе
упала раньше издателя, комментарий также предупреждает о возможных прежних записях.
Для восстановления используйте исходный артефакт: маркеры позволяют продолжить
без повторного создания issues, связей и комментариев; изменённый ответ отклоняется.
Причины включают согласование, доверенного автора, контекст, конфигурацию,
чтение и запись GitHub. Сырые исключения и ответы API не выводятся.
Ожидайте CI командой `gh pr checks <номер-PR> --watch`, без частого ручного опроса.
Сбой остаётся красным, готовый ответ и issues не публикуются.

Ответ ручного `/oc` принимается как JSON либо один целый блок `json` (также без языковой
метки); схема публикации остаётся строгой. Автоисправлений и автоматических
повторных запросов (repair) нет.
Локальная повторная проверка: `mise run test:scripts` с fake CLI, без модели.
Живой повтор `/oc` выполняет человек после review и merge; тесты не
устанавливают причину исторического сбоя без исходного потока.

## Работа с обращением

Ручной проход обращения:

1. В исходном issue написать `/oc примени скилл triage, предложи следующий шаг,
код пока не меняй` (также можно `/oc /triage`). Прочитать разбор и ответить
   на вопросы. Агент рекомендует метки, но пока не меняет их и не закрывает issues;
   воспроизведение в браузере в этом workflow недоступно.
2. Согласовать поведение и границы тестирования, затем написать
   `/oc примени скилл to-spec по этому обсуждению`. Агент публикует спецификацию
   с основным, негативным и соседним сценариями.
3. Написать `/oc примени скилл to-tickets к спецификации #123`.
   Агент сначала предлагает разбиение и зависимости. Ответить новым комментарием
   `/oc согласен с разбиением, опубликуй тикеты по скиллу to-tickets` либо
   запросить изменения.
4. Проверить опубликованные материалы и лично оставить итоговое согласование
   со ссылками в исходном issue. Агент не согласует результат за человека.
   Ссылку на согласование затем передать в PR реализации.

Спецификация и тикеты получают `ready-for-agent` и ссылки на исходное обращение
и запрос публикации; метка должна существовать в трекере. Тикеты становятся
sub-issues спецификации, зависимости — нативными blocked-by. В исходном issue
появляются ссылки на результат, в спецификации — комментарий со списком тикетов.
Родительские описания не переписываются. `implement-spec` из этого workflow
не выполняется.

## Автоматический разбор новых обращений

Событие `issues: opened` в том же workflow запускает предварительный триаж без
команды `/oc`. Допускается только автор `MeNn13` с ролью OWNER, MEMBER или
COLLABORATOR. Боты, закрытые issues и состояния `ready-for-agent`,
`ready-for-human`, `needs-info`, `wontfix` исключены. Обращения без состояния
либо с `needs-triage` допускаются. Поэтому спецификации и тикеты от `to-spec`
и `to-tickets`, помеченные `ready-for-agent`, повторно не разбираются.
Редактирование, повторное открытие и ответы в обсуждении автотриаж не запускают;
для продолжения используйте `/oc`.

Инструкция находится в [.github/opencode/triage-prompt.txt](../.github/opencode/triage-prompt.txt).
Агент читает скилл `triage` и код основной ветки, проверяет существующее поведение,
оставляет вопросы и рекомендует категорию и состояние. Комментарий начинается
с пометки AI. Метки, статус, код, спецификации и тикеты автоматически не меняются;
публикация спецификации или тикетов запрещена также издателем.
Для автотриажа модель возвращает Markdown, включая блоки кода внутри разбора,
а скрипт упаковывает его в `reply.json` с `publication: null`. Пустой,
незавершённый ответ или комментарий длиннее 50 000 символов отклоняется;
общий лимит потока CLI — 2 000 000 байт. JSONL потока CLI продолжает проверяться.
Строгий JSON-протокол ручного `/oc` не меняется.

Тайм-ауты общие с ручным вызовом: см. [выполнение и остановку](#выполнение-и-остановка).
Одновременно выполняется один автоматический разбор на issue; разные обращения обрабатываются
параллельно. Повторный запуск защищён маркером комментария от дублей.
Перед публикацией повторно проверяются автор, состояние и метки обращения.
Модель не получает GitHub-токен; отдельный издатель имеет `contents: read`
и `issues: write`, без прав записи в PR или код. Диагностика модели остаётся
в Actions и суточном артефакте; при сбое автоматического разбора комментарий
не публикуется. После устранения причины повторите failed jobs или вызовите `/oc`.

После слияния проверьте два новых issues: обычное обращение получает разбор,
issue с меткой `ready-for-agent`, заданной при создании, пропускает job модели.
Сохраните ссылки на обращения и прогоны Actions. Локальные фикстуры проверяют
фильтрацию и издателя, но не доказывают доступность модели и секретов в GitHub.
Если исправлялся код, создайте новое обращение после слияния: повтор старого
прогона может использовать прежнюю версию. Старое issue удалять не нужно;
свяжите новое с ним ссылкой.

Издатель проверяет весь результат и граф до создания issues. Маркеры публикации
защищают от дублей при повторе того же запроса. После частичного сбоя повторить
**Re-run failed jobs**: успешный job модели и его исходный артефакт сохраняются,
издатель достроит отсутствующие связи. Полный повтор модели с изменённым содержимым
отклоняется, если часть issues уже создана; новый комментарий — новый запрос,
а не повтор старой публикации. Артефакты доступны один день.

## Выполнение и остановка

Решение по **share: публикация сессий отключена** (`share: "disabled"`).
Полный поток модели не выводится в журнал и не загружается как артефакт.
Контекст и итоговый ответ передаются между заданиями через артефакты со сроком
хранения один день. Это данные публичного репозитория, без ключа.

Тайм-ауты: контекст — 5 минут, модель — 15, публикация — 5.
Новая допущенная команда отменяет предыдущую работу модели для этого issue/PR.
Повторные прогоны одного комментария также отменяют друг друга.
Издатель выполняется последовательно для одного issue/PR и не отменяет другой
издатель; при ручной отмене незавершённую публикацию нужно восстановить повтором.
Обычный или недоверенный комментарий не отменяет текущий ответ владельцу.
**Cancel workflow** останавливает прогон, **Disable workflow** — будущие вызовы.
Уже отправленный запрос может продолжиться у провайдера; ключ можно отозвать
в кабинете OpenCode.

## Приёмка workflow

После слияния workflow в основную ветку проверить:

1. В Settings → Secrets and variables → Actions задан `OPENCODE_API_KEY`.
2. В issue написать `/oc explain this issue` и найти ответ и успешный прогон.
3. Следующим комментарием попросить прочитать `docs/agents/` и назвать трекер,
   скиллы `to-spec`, `to-tickets`, `implement-spec` и команду проверок.
   Ожидаются `MeNn13/ai-for-developers-project-387` и `mise run check`.
4. Сохранить ссылки на комментарии и прогоны как доказательство приёмки.

Проверки скриптов подтверждают фильтры событий, контекст, разбор вывода CLI,
публикацию и восстановление на фикстурах GitHub API. Они не доказывают доступ
к провайдеру и живую публикацию. После слияния расширения пройти шаги выше
в исходном обращении и сохранить ссылки на созданные issues и Actions.
