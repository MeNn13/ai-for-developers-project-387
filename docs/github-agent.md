# Агент в GitHub Actions

## Аудит производительности

В **Settings → Secrets and variables → Actions** проекта 387 задайте `APP_URL`
с публичным HTTPS-адресом `/book` опубликованного приложения 387.
Переменная `AUDIT_STATUS_ISSUE` указывает на [журнал #70](https://github.com/MeNn13/ai-for-developers-project-387/issues/70).
Аудит по расписанию запускается в 06:17 по Москве при наличии обеих переменных.
Сервис Render из руководства по деплою связан с проектом 386. На момент переноса
публичный адрес деплоя 387 не подтверждён.
Для анализа используется секрет `OPENCODE_API_KEY`. После временной ошибки
DeepSeek V4.1 Flash Free первым резервом служит GPT-OSS 20B через Cloudflare
Workers AI, если заданы `CLOUDFLARE_API_KEY` (секрет) и `CLOUDFLARE_ACCOUNT_ID`
(переменная). На тарифе Workers Free модель использует бесплатную квоту Workers AI.
Следующий резерв — Gemini 3.1 Flash-Lite при наличии секрета `GEMINI_API_KEY`
из проекта Google AI Studio на бесплатном тарифе. Затем OpenCode пробует
Hy4 Flash Free, MiMo V2.6 Flash Free и Nemotron 3.5 Lightning Free.
На каждую модель отводится до двух минут.

В **Actions → Lighthouse audit → Run workflow** выберите `main` и режим `live`.
В Summary проверьте вывод OpenCode, а в Artifacts скачайте `lighthouse-report`.
В нём находятся исходный `lighthouse.json` и `collection.json` с итогом сбора.
При сбое сбора Summary и постоянный issue показывают «нет данных», а прогон
завершается ошибкой. OpenCode получает данные проверок производительности и
предлагает одну конкретную задачу, если отчёт даёт измеримое основание.
Издатель сверяет вывод с отчётом и публикует его через `GITHUB_TOKEN` с `issues: write`.

Дважды запустите `training` из `main`. Режим использует фиксированный синтетический
отчёт и доступен без `APP_URL`. Первый запуск публикует issue с префиксом
`[Учебный аудит]` по фиксированной синтетической находке. Второй ссылается на
тот же issue в Summary. Сохраните ссылки на прогоны и задачу в README и укажите,
что пришлось уточнить в настройках или инструкции агенту.

## Независимое авторевью PR

`opencode-review.yml` запускается при opened, synchronize, reopened и
ready_for_review, включая draft. Допускаются PR `MeNn13` и явно настроенного
приложения в ветках этого репозитория с целью в основной ветке. Человек задаёт переменные репозитория
`REVIEW_APP_LOGIN` и `REVIEW_APP_ID` (числовой ID пользователя Bot). Пустые
значения запрещают приложения; неизвестные боты и forks не получают ключ.

Ревью читает checkout базовой ревизии, diff передаётся текстом. Код PR не
исполняется. Основная модель — `opencode/deepseek-v4.1-flash-free`.
При распознанном ограничении запросов или квоты, отсутствии маршрута или
временной ошибке провайдера, включая HTTP 429 и 5xx, запускается одна новая
сессия с `cloudflare-workers-ai/@cf/openai/gpt-oss-20b`. Для неё нужны секрет
`CLOUDFLARE_API_KEY` и переменная `CLOUDFLARE_ACCOUNT_ID` этого репозитория.
Каждая сессия получает ключ своего провайдера. При неполных настройках
сохраняется исходная ошибка. Ошибки авторизации, разрешений, проверки ответа,
обнаружение ключа в ответе и неклассифицированный выход CLI завершают прогон.
Shell, изменение файлов и управление PR запрещены;
токен GitHub отсутствует в шаге модели. Права чтения: contents, issues, PR,
Actions, checks и statuses. OIDC не требуется. Издатель без модели имеет
contents: read и pull-requests: write, отправляет общий комментарий через gh
после сверки актуального head и доверия к автору.

В контекст входят [критерии календаря](../REVIEW.md) из доверенной базовой ревизии,
diff, связанные issues с обсуждениями, предыдущие ревью, построчные обсуждения
и результаты проверок текущего SHA.
Недоступные основания и незавершённые проверки отмечаются явно. Шаблон PR
требует ссылок на исходное обращение, спецификацию, тикеты и человеческое
согласование. Разобранные замечания учитываются при новом ревью.

Лимит задания независимого ревью — 30 минут. Новое событие того же PR отменяет старый запуск.
Ошибки шага модели сохраняют безопасный `diagnostic.json` и остаются красными.
Workflow вызывает `run` и `diagnosticFor` из доверенной базовой ревизии напрямую,
чтобы получить код ошибки даже при старом CLI-обработчике ревью без диагностики.
Артефакт `independent-review` сохраняется также при failure, кроме cancellation.
Издатель получает проверенный ответ и привязку к репозиторию, номеру PR и SHA.
В артефакт попадают проверенный комментарий и его привязка либо безопасная
диагностика. При переключении провайдера в журнале появляется фиксированное
сообщение. Если шаг **Run independent review** упал, откройте
`independent-review/diagnostic.json` или найдите его JSON-строку в логе шага.

- `submission_missing` версии 6 означает, что CLI не вывел события `submit_reply`.
- `submission_unfinished` версии 6 означает, что такие события были, но ни одно
  не содержало статуса `completed`. В обоих случаях `details.toolEvents` содержит
  число событий в пределах от 0 до 2 000 000.
- `reply_schema` означает, что завершённый вызов отклонён проверкой результата.
  В диагностике схемы видны только фиксированные правило, поле и причина.
- `reply_sensitive` означает, что комментарий содержал точное значение
  настроенного ключа и был отклонён.

Нулевой счётчик характеризует поток CLI. Он не показывает, был ли инструмент
доступен модели. Исторический `submission_missing` версии 1 объединяет первые
два исхода. Точную причину старого сбоя по этому коду восстановить нельзя.
Остановка вручную: Actions → independent-review → Cancel workflow. Авторевью
не расходует бюджет ручных команд реализации. Его комментарии от бота не
вызывают реализацию. Решения по замечаниям и мердж принимает человек.

Локальные fake API/CLI тесты проверяют допуск, контекст и публикацию. Ревью
инфраструктурного PR запускает код его доверенной базы. После человеческого мержа
и настройки приложения нужен свежий допустимый PR от App. Проверьте, что в PR
ровно один комментарий независимого ревью для текущего head SHA, и сохраните
ссылки на комментарий и запуск Actions. Если шаг модели упал, сохраните ссылку
на прогон и безопасный код из диагностики. Живая приёмка требует опубликованного
комментария для актуального SHA.

## Независимая браузерная приёмка

Workflow [browser-acceptance.yml](../.github/workflows/browser-acceptance.yml)
запускается отдельно при открытии, обновлении и повторном открытии PR, а также
при переводе из draft. Он явно получает head SHA автора, сверяет фактический
`git HEAD` и запускает существующие E2E на настоящем локальном API и собранном
frontend в Chromium. Ключ модели и токен записи не передаются; checkout не
сохраняет credentials. Существующие тесты создают данные через интерфейс.

В Actions откройте запуск `browser-acceptance` и скачайте артефакт
`browser-pr-<PR>-<SHA>-<run>-<attempt>` (хранится семь дней). В `evidence.json`
проверьте `result: success`, номер PR, ссылку на запуск, равенство `expectedSha`
и `actualSha` текущему head PR. Список `scenarios` содержит реально выполненные
сценарии и результаты. Откройте соответствующий `trace.zip` через
`mise exec -- npx playwright show-trace <путь-к-trace.zip>` и оцените действия
и результат. Trace сохраняется явно и при успехе, отчёт Playwright и диагностика
доступны в том же артефакте. Ошибка SHA, отсутствие отчёта или успешного trace
делают проверку неуспешной; при раннем сбое часть диагностики может отсутствовать.

После нового push дождитесь нового запуска и артефакта с новым SHA. Повтор
старого запуска не подтверждает новый head; для того же SHA доступен Re-run jobs.
Отсутствие артефакта при раннем авторевью означает, что свидетельства ещё нет.
Будущие основной и соседний сценарии добавляются по спецификации самой фичи;
эта проверка подтверждает инфраструктуру существующими E2E.

Живая приёмка изменения требует отдельного PR: проверить успешный запуск,
скачивание trace при успехе и соответствие SHA после следующего push. Локальные
фикстуры скрипта проверяют формирование результата и отказы, но не подтверждают
сохранение артефакта сервисом Actions. Перед публикацией обязателен полный check.

## Ручной вызов и доступ

Workflow [opencode.yml](../.github/workflows/opencode.yml) отвечает на команды
`/oc` и `/opencode` в начале нового комментария к issue, PR или строке diff.
Регистр команды не важен; редактирование комментария не запускает агента.
Пример: `/oc explain this issue`.

Вызов разрешён только `MeNn13`; список `allowedUsers` находится в
`scripts/opencode-publish.mjs` (общий для допуска и издателя). Для расширения
добавить GitHub-логин в список и слить
изменение. Участник также должен иметь роль OWNER, MEMBER или COLLABORATOR.
Комментарии ботов и обращения к PR из fork игнорируются. Недопущенные вызовы
не получают ключ модели.

Используется OpenCode CLI **2.2.3** с проверкой SHA-256 релизного архива,
модель — **`opencode/deepseek-v4.1-flash-free`**. Ключ хранится только в секрете
репозитория **`OPENCODE_API_KEY`**. Карта, пополнение и платные модели не нужны.
Бесплатный доступ ограничен условиями провайдера и может закончиться; при
лимите или недоступности модели прогон завершается ошибкой, платного резерва нет.
Основная модель и вспомогательные агенты явно используют ту же бесплатную модель.

Это собственный workflow с CLI: прежний OpenCode GitHub Action
[больше не поддерживается](https://github.com/anomalyco/opencode/pull/59032).
Установленное OpenCode GitHub App для этого варианта не используется.
Авторизация GitHub — встроенный `GITHUB_TOKEN`, поэтому `id-token: write`
не нужен. Checkout имеет `persist-credentials: false`. Задания получения контекста
и модели имеют только права чтения; отдельное задание публикации имеет
`issues: write` и `pull-requests: write`. Оно запускает проверенный скрипт издателя
из той же ревизии основной ветки, не запускает модель и не исполняет её вывод.

Агент читает код основной ветки,
`AGENTS.md`, `docs/agents/`, глоссарий, ADR и проектные скиллы из `.agents/skills`.
По явному запросу применяет скиллы `triage`, `to-spec` и `to-tickets`; отдельного
парсера команд скиллов нет. Модель готовит текст и структурированный результат,
а отдельный `publish` создаёт спецификацию или согласованные тикеты в этом
репозитории. Изменения кода и PR отключены. Shell, редактирование, субагенты
и MCP запрещены. Для PR передаётся diff как текст, код его ветки не исполняется.
GitHub-токен не передаётся процессу модели. Настройки локального Codex остаются
отдельными от конфигурации CI в `.github/opencode/opencode.json`.

Ответ появляется обычным комментарием от `github-actions[bot]` со ссылкой на
прогон; комментарии к diff также получают ответ в общем обсуждении PR.
Вкладка **Actions → opencode** показывает состояние. Передаются описание,
обсуждение до вызывающего комментария и, для PR, diff и соответствующая ветка
review-обсуждения. Ревизия основной ветки записывается в контекст вызова.
Для issue также загружаются связанные issues текущего репозитория с обсуждениями:
ссылки вида `#123` и полные URL, на два уровня, не более 30 связанных issues.
Удалённые и недоступные связанные issues отмечаются в контексте явно;
обычное обсуждение продолжается, публикация тикетов по ним запрещена.
Слишком большой контекст отклоняется явно. Следующий вызов заново читает
обсуждение; скрытая память предыдущей сессии не используется.

## Диагностика и восстановление

При сбое подготовки в логах остаётся только безопасная диагностика,
а отдельный `opencode-diagnostic` с `diagnostic.json` хранится один день и
передаётся издателю даже при failure (кроме cancellation). Категории: запуск и
выход CLI, размер и JSONL потока, незавершённый ответ, отсутствие событий,
незавершённые вызовы или конфликт результатов `submit_reply`, схема ответа,
отклонение комментария ревью с ключом (`reply_sensitive`), историческая диагностика JSON,
ошибка провайдера, чтение/запись файлов, конфигурация и неизвестная ошибка.
Авторизация и HTTP 429 различаются только по структурированному статусу
провайдера; текст ошибки не служит доказательством исчерпания лимитов.
Сырые ответы, stderr, контекст и ключи в диагностику не попадают.

Если CLI завершился с ошибкой и вернул событие `provider.no-route`,
в `diagnostic.json` появится код `model_unavailable`. Проверьте доступность
выбранной модели в [каталоге OpenCode Zen](https://opencode.ai/zen/v1/models).
Для остальных ошибок завершения сохраняется `cli_exit`. При обычном ненулевом
коде выхода поле `exitCode` содержит его числовое значение.
Историческая диагностика `reply_json` версии 2 содержит `details`: размеры `streamBytes` и
`answerBytes` в UTF-8, `candidateChars` и `position` в единицах UTF-16
(позиция может быть `null`), счётчики `eventCount`, `textEventCount`,
`messageCount`, `finalTextEventCount`, фиксированные категории `wrapper`,
`root` и `parseKind`. Идентификаторы сообщений и текст ошибки не сохраняются.
Для `reply_schema` версия 2 содержит только `details.rule` — фиксированный
код первого нарушенного правила: `version_comment`, `publication_kind`,
`publication_items`, `spec_item_count`, `ticket_references`, `item_key`,
`item_text`, `item_blockers`, `blocker_order`, `spec_blockers`.
Непредвиденное исключение валидатора обозначается `schema_other`.
Значения полей ответа и текст исключения не сохраняются. Эта диагностика
не восстанавливает причину прежнего сбоя без исходного ответа модели.
`submission_missing` и `submission_unfinished` используют версию 6
с ограниченным счётчиком `details.toolEvents`. Оба кода применяются и в ручном
`/oc`, и в независимом ревью. Издатель по-прежнему понимает исторические
`submission_missing` и `reply_schema` версии 1.
Новая диагностика схемы версии 3 содержит только фиксированные `rule`, `field`
и `reason`: `missing`, `type`, `empty`, `too_long`, `invalid`, `duplicate_key`,
`duplicate_dependency`, `reference`. Комментарий на русском объясняет причину
и называет поле, не раскрывая его значение. Старые версии 1/2 читаются по-прежнему.
Для диагностики откройте Actions по ссылке комментария, затем прочитайте только
`opencode-diagnostic/diagnostic.json`; сырой вывод модели для этого не нужен.
Синтетические тесты проверяют программу на вымышленных ответах и не доказывают,
что будущая модель соблюдёт протокол.
Размер диагностики ограничен 1024 байтами. Счётчики не доказывают причину
сбоя сборки потока и не восстанавливают причины исторических ошибок.
При сбое подготовки состояние публикации проверяется отдельно: сам отказ
модели не доказывает ни наличие, ни отсутствие результатов прежнего прогона.
При отсутствии или некорректной диагностике выводится общее сообщение.
Диагностика публикации версии 3 содержит фиксированные `reason` и `state`:
`none` означает, что восстановление проверено и записи ещё не отправлялись,
`possible` — найдены прежние объекты или уже отправлена запись,
`unknown` — прежнюю публикацию исключить нельзя. Ошибка первой записи считается
возможной публикацией даже при потере ответа GitHub. Если подготовка при повторе
упала раньше издателя, история проверяется по маркерам той же операции.
Для восстановления используйте исходный артефакт: маркеры позволяют продолжить
без повторного создания issues, связей и комментариев; изменённый ответ отклоняется.
Причины включают согласование, доверенного автора, контекст, конфигурацию,
чтение и запись GitHub. Сырые исключения и ответы API не выводятся.
Ожидайте CI командой `gh pr checks <номер-PR> --watch`, без частого ручного опроса.
Сбой остаётся красным, готовый ответ и issues не публикуются.

Историческая диагностика JSON версии 4 сохраняет прежние структурные счётчики и добавляет
закрытые категории: не JSON, неподдерживаемая Markdown-обёртка/текст вне JSON,
лишнее содержимое после JSON, неверное экранирование/управляющий символ,
синтаксис внутри документа, ошибка на конце документа, неклассифицированный
синтаксис. Комментарий объясняет наблюдаемое нарушение без текста исключения.
Известная позиция — offset от нуля в UTF-16, строка и столбец от единицы
относительно JSON-кандидата после удаления допустимого fence. При неизвестной
позиции это указано явно. Линейный проход с учётом строк и escape сообщает
только вид незакрытой структуры: объект, массив или строка. Это диагностика,
а допуск в том протоколе выполняли JSON.parse и валидатор схемы.
Ошибка на конце документа не доказывает обрезку ответа провайдером.
Версии 1–3 читаются по имеющимся данным без восстановления отсутствующих сведений.
Неизвестные поля, невозможные координаты и превышение 1024 байт дают фиксированный
осторожный fallback. Ни значения, ни названия полей модели не сохраняются.

Перед сообщением об отказе подготовки workflow сверяет контекст с событием и
читает issues и комментарии исходного обращения через GitHub API: до 100 страниц
по 100 элементов для каждого списка. `none` допустим только после полной проверки
без маркеров операции; `possible` означает прежние результаты или отправленную
запись; `unknown` — непроверенный контекст, недоступную или неполную историю.
Сам диагностический комментарий не считается публикацией спецификации.
При `none` и некорректном reply.json результата для восстановления нет:
повтор одного издателя не поможет; передайте Actions для диагностики подготовки.
При `possible` сохраните созданные issues и восстанавливайте издателя с исходным
корректным артефактом. При `unknown` сначала проверьте созданное и историю;
слепой повтор не рекомендуется. Автоматических повторов модели нет.

Наблюдения #47 из прогонов 43753832240 и 43754269348 содержат только безопасные
метаданные v2. Сырой ответ отсутствует: точную причину и исторический payload
восстановить нельзя. Синтетические примеры этих классов отказа не являются
историческими ответами. Прогон 44097016852 также упал при разборе итогового текста.
Теперь этот текст не используется для передачи результата. Живую проверку после
merge запускают новым комментарием в #47.

Все ручные ответы `/oc` передаются через локальный инструмент `submit_reply`:
обычный комментарий, одна спецификация или согласованные тикеты с зависимостями.
Плагин из доверенного checkout передаёт модели JSON-схему аргументов и проверяет
их общим валидатором. Markdown хранится в строках `comment` и `body`; инструмент
возвращает только подтверждение, не пишет файлы и не обращается к GitHub.
Разрешены только действие `submit_reply` и ресурс политики `submit_reply:reply`.
Для обсуждений и независимого ревью `scripts/opencode-config.mjs` добавляет
плагин с абсолютным путём и узкие разрешения перед записью в `/etc/opencode`.
Задания реализации используют базовый конфиг без этого инструмента.
Новые npm-зависимости не нужны.

Скрипт принимает аргументы успешного события `tool_use`, повторно проверяет их и
записывает `reply.json` только после успешного завершения CLI и потока. Финальный
текст модели игнорируется и не обязателен; извлечения JSON из Markdown нет.
Дубли событий определяются по сессии, сообщению и вызову. Первый корректный
результат неизменяем: одинаковые повторные вызовы разрешены независимо от порядка
ключей объекта, другой результат блокирует весь прогон (`submission_conflict`).
При отсутствии события скрипт сообщает `submission_missing`, при событиях
без успешного завершения — `submission_unfinished`. Неверные аргументы можно
исправить в той же сессии в пределах 20 шагов и тайм-аута 15 минут. Промпт
независимого ревью требует явного `publication: null`.
Для ручных ответов автоматических повторных запросов нет. Старый `reply.json` удаляется до запуска,
при отказе подготовки новый артефакт публикации не создаётся. Автотриаж продолжает
принимать Markdown без инструмента. Издатель и его проверки согласования не меняются.
Локальная повторная проверка: `mise run test:scripts` с fake CLI, без модели.
Живой повтор `/oc` выполняет человек после review и merge; тесты не
устанавливают причину исторического сбоя без исходного потока.

## Работа с обращением

Ручной проход обращения:

1. В исходном issue написать `/oc примени скилл triage, предложи следующий шаг,
код пока не меняй` (также можно `/oc /triage`). Прочитать разбор и ответить
   на вопросы. Агент рекомендует метки, но пока не меняет их и не закрывает issues;
   воспроизведение в браузере в этом workflow недоступно.
2. Согласовать поведение и границы тестирования, затем написать
   `/oc примени скилл to-spec по этому обсуждению`. Агент публикует спецификацию
   с основным, негативным и соседним сценариями.
3. Написать `/oc примени скилл to-tickets к спецификации #123`.
   Агент сначала предлагает разбиение и зависимости. Ответить новым комментарием
   `/oc согласен с разбиением, опубликуй тикеты по скиллу to-tickets` либо
   запросить изменения.
4. Проверить опубликованные материалы и лично оставить итоговое согласование
   со ссылками в исходном issue. Агент не согласует результат за человека.
   Ссылку на согласование затем передать в PR реализации.

Спецификация и тикеты получают `ready-for-agent` и ссылки на исходное обращение
и запрос публикации; метка должна существовать в трекере. Тикеты становятся
sub-issues спецификации, зависимости — нативными blocked-by. В исходном issue
появляются ссылки на результат, в спецификации — комментарий со списком тикетов.
Родительские описания не переписываются. Явный `implement-spec` передаётся
выключенному по умолчанию маршруту [исходной реализации](github-agent-initial.md).

## Автоматический разбор новых обращений

Событие `issues: opened` в том же workflow запускает предварительный триаж без
команды `/oc`. Допускается только автор `MeNn13` с ролью OWNER, MEMBER или
COLLABORATOR. Боты, закрытые issues и состояния `ready-for-agent`,
`ready-for-human`, `needs-info`, `wontfix` исключены. Обращения без состояния
либо с `needs-triage` допускаются. Поэтому спецификации и тикеты от `to-spec`
и `to-tickets`, помеченные `ready-for-agent`, повторно не разбираются.
Редактирование, повторное открытие и ответы в обсуждении автотриаж не запускают;
для продолжения используйте `/oc`.

Инструкция находится в [.github/opencode/triage-prompt.txt](../.github/opencode/triage-prompt.txt).
Агент читает скилл `triage` и код основной ветки, проверяет существующее поведение,
оставляет вопросы и рекомендует категорию и состояние. Комментарий начинается
с пометки AI. Метки, статус, код, спецификации и тикеты автоматически не меняются;
публикация спецификации или тикетов запрещена также издателем.
Для автотриажа модель возвращает Markdown, включая блоки кода внутри разбора,
а скрипт упаковывает его в `reply.json` с `publication: null`. Пустой,
незавершённый ответ или комментарий длиннее 50 000 символов отклоняется;
общий лимит потока CLI — 2 000 000 байт. JSONL потока CLI продолжает проверяться.
Строгий JSON-протокол ручного `/oc` не меняется.

Тайм-ауты общие с ручным вызовом: см. [выполнение и остановку](#выполнение-и-остановка).
Одновременно выполняется один автоматический разбор на issue; разные обращения обрабатываются
параллельно. Повторный запуск защищён маркером комментария от дублей.
Перед публикацией повторно проверяются автор, состояние и метки обращения.
Модель не получает GitHub-токен; отдельный издатель имеет `contents: read`
и `issues: write`, без прав записи в PR или код. Диагностика модели остаётся
в Actions и суточном артефакте; при сбое автоматического разбора комментарий
не публикуется. После устранения причины повторите failed jobs или вызовите `/oc`.

После слияния проверьте два новых issues: обычное обращение получает разбор,
issue с меткой `ready-for-agent`, заданной при создании, пропускает job модели.
Сохраните ссылки на обращения и прогоны Actions. Локальные фикстуры проверяют
фильтрацию и издателя, но не доказывают доступность модели и секретов в GitHub.
Если исправлялся код, создайте новое обращение после слияния: повтор старого
прогона может использовать прежнюю версию. Старое issue удалять не нужно;
свяжите новое с ним ссылкой.

Издатель проверяет весь результат и граф до создания issues. Маркеры публикации
защищают от дублей при повторе того же запроса. После частичного сбоя повторить
**Re-run failed jobs**: успешный job модели и его исходный артефакт сохраняются,
издатель достроит отсутствующие связи. Полный повтор модели с изменённым содержимым
отклоняется, если часть issues уже создана; новый комментарий — новый запрос,
а не повтор старой публикации. Артефакты доступны один день.

## Выполнение и остановка

Решение по **share: публикация сессий отключена** (`share: "disabled"`).
Полный поток модели не выводится в журнал и не загружается как артефакт.
Контекст и итоговый ответ передаются между заданиями через артефакты со сроком
хранения один день. Это данные публичного репозитория, без ключа.

Тайм-ауты: контекст — 5 минут, модель — 15, публикация — 5.
Новая допущенная команда отменяет предыдущую работу модели для этого issue/PR.
Повторные прогоны одного комментария также отменяют друг друга.
Издатель выполняется последовательно для одного issue/PR и не отменяет другой
издатель; при ручной отмене незавершённую публикацию нужно восстановить повтором.
Обычный или недоверенный комментарий не отменяет текущий ответ владельцу.
**Cancel workflow** останавливает прогон, **Disable workflow** — будущие вызовы.
Уже отправленный запрос может продолжиться у провайдера; ключ можно отозвать
в кабинете OpenCode.

## Приёмка workflow

После слияния workflow в основную ветку проверить:

1. В Settings → Secrets and variables → Actions задан `OPENCODE_API_KEY`.
2. В issue написать `/oc explain this issue` и найти ответ и успешный прогон.
3. Следующим комментарием попросить прочитать `docs/agents/` и назвать трекер,
   скиллы `to-spec`, `to-tickets`, `implement-spec` и команду проверок.
   Ожидаются `MeNn13/ai-for-developers-project-387` и `mise run check`.
4. Сохранить ссылки на комментарии и прогоны как доказательство приёмки.

Проверки скриптов подтверждают фильтры событий, контекст, разбор вывода CLI,
публикацию и восстановление на фикстурах GitHub API. Они не доказывают доступ
к провайдеру и живую публикацию. После слияния расширения пройти шаги выше
в исходном обращении и сохранить ссылки на созданные issues и Actions.

## Диагностика исходной реализации

Actions Summary и артефакты `initial-check-diagnostic` и
`initial-publish-diagnostic` сохраняют этап, категорию, базовый и кандидатный SHA.
`provider_error` может включать HTTP-статус, а `model_exit` — код выхода CLI.
`timeout`, `empty_diff`, `file_rules`, `generation_failed` и `check_failed`
различают срок, отсутствие изменений, нарушение правил файлов, генерацию
и проверку. Для публикации категория дополняется состоянием записи.
`check_failed` включает имя упавшей задачи верхнего уровня mise, если
изолированная проверка дошла до её выполнения.
CI проверяет успешный и отклонённый кандидат в задаче `implementation-candidate`.

В [запуске 44756999772](https://github.com/MeNn13/ai-for-developers-project-387/actions/runs/44756999772)
контекст прошёл, но вызов модели для #57 завершился с `category=unknown`.
Сохранился только контекст, поэтому конкретный ответ CLI или провайдера установить
по этому запуску нельзя. Новый сценарий выполняет согласованный граф одним сеансом,
сохраняет диагностику отдельно и допускает издателя только после проверки точного SHA.
Этот сценарий прошёл в
[тестовом репозитории](https://github.com/MeNn13/booking-calendar-opencode-v1-acceptance/actions/runs/45387886835).

После мержа в 387 сначала проверьте обсуждение и триаж на учебной задаче, затем
реализацию с новым явным согласием, одобрением окружения издателя и проверками
авторевью и браузера на опубликованном SHA. Для Lighthouse проверьте два
учебных запуска и живой запуск после настройки адреса и резерва Cloudflare.
Ссылки на прогоны 387 добавьте в журнал аудита и в обращение о реализации.
Для остановки реализации выключите `IMPLEMENTATION_INITIAL_ENABLED`, для
остановки аудита отключите workflow. Откат кода выполняется отдельным PR.

Кандидат и издатель разрешают правки существующих корневых
`GLOSSARY.md` и `README.md`. При изменении контракта модель передаёт
`contract/main.tsp`, а контроллер добавляет OpenAPI, клиент TypeScript и DTO C#
из штатного генератора в тот же коммит.
